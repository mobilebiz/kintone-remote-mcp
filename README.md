# kintone Remote MCP Server

kintone の公式 MCP サーバー [`@kintone/mcp-server`](https://github.com/kintone/mcp-server) を、
**インターネット越しに使えるリモート MCP サーバー**にしたものです。

**スマートフォンの Claude アプリから自分の kintone を呼ぶ**ことを目的に作りました。

```
スマホの Claude ─── HTTPS ───▶ このサーバー ─── OAuth ───▶ cybozu.com
                                     │
                                     └─── kintone REST API
```

## 公式のものとの違い

公式の MCP サーバーは**手元で動かす**前提です（stdio）。
そのため、デスクトップの Claude からは使えますが、**スマホからは使えません**。

| | 公式 (`@kintone/mcp-server`) | これ |
| --- | --- | --- |
| 動かす場所 | 手元のパソコン | Cloud Run |
| つなぎ方 | stdio | Streamable HTTP |
| 認証 | 環境変数に置いた資格情報 | **cybozu.com の OAuth** |
| スマホから | 使えない | **使える** |
| 資格情報の置き場所 | 手元の設定ファイル | 暗号化して Firestore |

ツールの実装そのものは公式のものをそのまま使っています。
このリポジトリが足しているのは、**認可・保管・上限・監査**の層です。

## 仕組み

このサーバーは **OAuth 2.1 の認可サーバーを兼ねます**。
実際の認証は cybozu.com へ委ねます（ブリッジ方式）。

1. Claude がこのサーバーに繋ぎにくる
2. 同意画面で「何を許可するか」を見せる
3. cybozu.com のログインへ送る
4. 戻ってきた kintone のトークンを**暗号化して保管**し、Claude には**このサーバーのトークン**を返す

**Claude が kintone のトークンを持つことはありません。**

> [!WARNING]
> **Claude 側で接続を消しても、このサーバーには届きません。**
>
> 失効の要求（RFC 7009）を受ける口は用意してありますが、
> **Claude はそれを呼びません**（実機で確認：接続を削除しても要求が1件も来ない）。
> 保管した kintone のリフレッシュトークンは**残ります**。
>
> 消す手立ては3つです。
>
> 1. **待つ** — 接続の絶対期限（400日）で失効し、保存層からも消えます
> 2. **cybozu 側で切る** — 共通管理の OAuth クライアントで利用者を外すか、
>    クライアントごと消します。**こちらのほうが確実です**（トークンが無効になります）
> 3. **運用者が消す** — 監査ログの `accountId` で Firestore のレコードを消します
>
> 利用者が自分で消す方法は**ありません**。
> このサーバーは kintone のユーザー名を保存しないので、
> 「この人の接続」を特定できないためです。

## 必要なもの

- Google Cloud プロジェクト（Cloud Run / Firestore / Secret Manager / Cloud KMS）
- **cybozu.com 共通管理者の権限**（OAuth クライアントの登録に要ります）
- Node.js 22 以上（開発するとき）

## はじめかた

手順は **[docs/deployment.md](docs/deployment.md)** にあります。設定の一覧は [.env.example](.env.example) です。

大きな流れはこうです。

1. Firestore（専用データベース）と、専用のサービスアカウントを作る
2. 鍵類を Secret Manager に入れる
3. **非公開で1度デプロイして URL を確定させる**
4. その URL を使って、cybozu.com に OAuth クライアントを登録する
5. 設定を入れて公開する

> [!IMPORTANT]
> **3 と 4 の順序は入れ替えられません。** cybozu 側に登録するリダイレクト先は
> デプロイするまで決まらず、`ALLOWED_HOSTS` は URL が決まるまで設定できません。

## 使えるツール

公式サーバーの27ツールのうち、**OAuth で実行できるものだけ**を公開します。

| 種別 | 既定 | 環境変数 |
| --- | --- | --- |
| レコードの参照 | **有効** | `ENABLE_RECORD_READ` |
| アプリ設定の参照 | **有効** | `ENABLE_APP_READ` |
| レコードの登録・更新 | 無効 | `ENABLE_RECORD_WRITE` |
| アプリ設定の変更 | 無効 | `ENABLE_APP_WRITE` |
| 削除系 | 無効 | `ALLOW_DESTRUCTIVE` |

> [!NOTE]
> **削除は `ALLOW_DESTRUCTIVE` で別扱いにしています。**
> cybozu 側のスコープでは、登録・更新・削除がすべて `k:app_record:write` に含まれ、
> **削除だけを止める手段がありません**。このフラグが唯一の歯止めです。

### スペース操作と検索（連携用ユーザーが要ります）

次の5つは **OAuth では実行できません**（cybozu がスコープを用意していないため）。

- `kintone-get-space` / `kintone-update-space` / `kintone-delete-space`
- `kintone-add-space-from-template`
- `kintone-search`

> [!CAUTION]
> **`kintone-search` は「API ラボ」の API を使います。
> サイボウズは、テスト環境だけでの利用を推奨しています。**
>
> 画面にこう書かれています。
>
> > API ラボで提供するAPIは、リリースせずに開発を取りやめる場合や、
> > 今後仕様を大きく変更する場合があります。そのため、
> > **テスト環境だけでの利用を推奨します。**
>
> つまり `ENABLE_SEARCH=true` は、**提供元が本番利用を勧めていない API に
> 依存する**という選択です。ある日動かなくなっても、それは仕様どおりです。
> 既定で無効にしてあるのはこのためです。
>
> **有効化の場所**: kintone システム管理 → その他 → アップデートオプション →
> 「検討中の新機能」→ **API ラボ**。
>
> ⚠ **cybozu.com 共通管理の「アップデートオプション」ではありません。**
> 同じ名前の画面が両方にあります（実際に取り違えました）。
> 入口は **kintone 側の歯車**です。
>
> 有効にしていないと `400 GAIA_OF02` で必ず失敗します（実測）。
> `ENABLE_SEARCH=true` はこちら側のスイッチにすぎません。

実行するにはパスワード認証が要ります。
`KINTONE_INTEGRATION_USERNAME` と `KINTONE_INTEGRATION_PASSWORD` を設定すると、
**この5つだけ**がそのユーザーとして実行されます。設定しなければ公開されません。

> [!NOTE]
> **`kintone-get-space` は実環境で動かしました**（2026-09-18）。
> **更新・作成・削除と `kintone-search` は、まだ一度も実行していません。**
> 自動テストはあります（`tests/adapter/integration-user.test.ts`）。

> [!WARNING]
> **これらは、接続した本人ではなく連携用ユーザーとして実行されます。**
>
> - **本人が見られないものにも手が届きます。** 連携ユーザーの権限が効きます。
>   **これは実測です**（2026-09-18）。第三者が管理する非公開スペースに
>   連携ユーザーだけが参加している状態で、**非メンバーの本人に中身が返りました**
> - **`kintone-search` は、kintone のアプリ権限を通り抜けます。**
>   同じ利用者・同じ会話・同じアプリに対して、
>   `kintone-get-records` は **`403`** で拒否されたのに、
>   `kintone-search` は**中身を返しました**（実測）。
>   検索結果には検索語の周辺テキストが含まれるので、
>   **レコードを取得するまでもなく漏れます**
> - **パスワード認証にはスコープがありません。** そのユーザーができること全部です。
>   **権限を絞った専用ユーザー**を用意してください
> - **2要素認証を有効にしたユーザーでは使えません**（REST API が実行できません）。
>   サイボウズも連携用の専用ユーザーを勧めています
>
> 同意画面には「あなたではなく連携用ユーザーとして実行されます」と表示され、
> 監査ログにも `identity` として残ります。

> [!NOTE]
> **スペースの公開範囲（`isPrivate`）は変更できません。**
>
> `kintone-update-space` は公開／非公開を切り替えられますが、
> **このサーバーからは拒否します**（`ENABLE_SPACE_WRITE` を有効にしても）。
>
> 削除ではないので `ALLOW_DESTRUCTIVE` では止まらず、
> データも消えません。**ですが、見えなかったものが全社に見えるようになります。**
> 消えるより気づきにくい。スペース名の変更と公開範囲の変更は、
> 利用者にとって別物なので、同じ許可でまとめていません。
>
> 変更するときは kintone の画面から行ってください。

> [!NOTE]
> **`ALLOWED_APP_IDS` でアプリを絞っているときは、アプリ境界を課せないツールを公開しません。**
>
> 引数にアプリ ID を持たないツールは、境界の判定が素通りします。
> 「拒否している」ように見えて、実際には何も見ていません。該当するのは次の7つです。
>
> - スペース操作4つと `kintone-search`（連携ユーザーの広い権限とも重なります）
> - `kintone-add-app` — **許可リストの外にアプリを作れてしまいます**
> - `kintone-download-file` — `fileKey` だけで**どのアプリの添付でも落とせます**
>
> 絞っていないときは、いずれも通常どおり公開されます。

## 接続の寿命

- kintone のアクセストークン: 1時間（自動で更新します）
- Claude に渡すアクセストークン: 1時間 / リフレッシュトークン: 30日（使うたびに更新）
- **接続そのもの: 400日**

> [!NOTE]
> **接続の寿命は更新で延びません。** 使い続けていても、
> 最初に認可してから400日でつなぎ直しが要ります。
> 期限が来ると、保管していた kintone の資格情報も読み出せなくなり、
> 保存層からも自動で消えます。
>
> 期限の記録が無い接続（この仕組みより前に作られたもの）は、
> **2027-10-22 に切れます**。

## 同意した範囲

**同意した時点で公開されていたツールを記録し、実行時は現在の設定との積を取ります。**

つまり、あとから設定を広げても（たとえば削除を有効にしても）、
**既に繋いである接続には及びません**。新しい権限を使うには、
利用者がつなぎ直して同意し直す必要があります。

逆に設定を狭めた場合は、同意があっても公開されません。

**対象アプリ（`ALLOWED_APP_IDS`）も同意に含まれます。** 「対象アプリ: 1」で
同意した接続は、設定を `2` に変えてもアプリ2へは届きません。

> [!IMPORTANT]
> **`CYBOZU_OAUTH_SCOPES` を広げたときも、つなぎ直しが要ります。**
> これは同意の仕組みとは別の話で、**cybozu 側の都合**です。
> スコープはトークンを発行した時点で決まるので、
> あとから広げても**既に発行されているトークンには及びません**。
>
> 実際に踏みました。書き込みを有効にしたあと、既存の接続から更新すると
> `403` / `CB_OA01` が返ります。つなぎ直すと通ります。

> [!NOTE]
> **同意の仕組みを入れる前に作られた接続**には、移行時点で確定した範囲
> （削除と、連携ユーザーとして動く操作を除いたもの）が適用されます。
> それらを使うには、つなぎ直して同意し直してください。
>
> この範囲は**固定**です。あとから対応ツールが増えても、広がりません。

## 守れること・守れないこと

正直に書きます。

**守れること**

- kintone のトークンは AES-256-GCM で暗号化し、**暗号文を接続に束縛**します（別レコードへの差し替えを検出）
- 暗号鍵は **Cloud KMS で包み**、設定には暗号文しか置きません
- `code` や `state` をアプリ側のログに出しません（伏せ字は許可リスト方式）
- 接続ごとに独立していて、1つを切っても他は生きます
- **スペースの公開範囲は変更させません**（書き込みを許可していても）

**守れないこと**

- **復号権限を持つサービスアカウントを奪われたら、鍵は取り出せます。**
  KMS が守るのは「保存されている設定やデータだけが漏れた場合」です
- **上限はインスタンスをまたいで効きません。** プロセス内のメモリで数えているので、
  「これ以上は出ない」と言える数は存在しません（[負荷予算](docs/deployment.md)を参照）
- **Cloud Logging のリクエストログは、アプリ側では伏せられません。**
  `code` と `state` は `httpRequest.requestUrl` に載ります。
  **sink の除外を自分で設定してください**（[手順](docs/deployment.md)）。
  コードからは適用できません
- **kintone 側の権限は、接続した本人のもの**がそのまま効きます。
  このサーバーが権限を足すことはありませんが、減らすのも `ALLOWED_APP_IDS` 程度です
- **アプリを守っているのは、スペースの公開設定ではなくアプリのアクセス権です。**
  下の「[kintone の設定が、そのまま見えます](#kintone-の設定がそのまま見えます)」を読んでください
- **ただし連携用ユーザーを設定した場合、スペース操作と検索だけは別です。**
  そこは本人ではなく連携ユーザーの権限で動きます（上の警告を参照）
- **利用者が自分で接続を切ることはできません。** Claude 側で消しても
  こちらには届かず（実機で確認）、こちらは kintone のユーザー名を保存しないので
  「この人の接続」を特定できません。**残るのは400日の絶対期限と、
  cybozu 側で切ること**です（[上の警告](#仕組み)を参照）

## kintone の設定が、そのまま見えます

このサーバーは権限を足しませんが、**既存の設定の緩さを可視化します**。
実際に踏んだものを2つ書いておきます。どちらも kintone の仕様どおりで、
このサーバーの欠陥ではありません。**それでも、知らずに公開すると驚きます。**

### スペースの公開設定とアプリのアクセス権は、別の軸です

kintone では、この2つが独立しています。

| 軸 | 何を隠すか |
| --- | --- |
| スペースの公開／非公開 | **スペース**（ポータル・スレッド） |
| アプリのアクセス権 | **アプリ**（レコード） |

`kintone-get-apps` が使う API の必要な権限は、
[**アプリのレコード閲覧権限または追加権限**](https://cybozu.dev/ja/kintone/docs/rest-api/apps/get-apps/)で、
**スペースのメンバーであることは条件に入っていません**。

**実測（2026-09-18）:** 非公開スペースの中に連携ユーザーがアプリを作り、
レコードを1件入れ、**そのスペースの非メンバー**が自分のトークンで読もうとしました。

| 操作 | 結果 |
| --- | --- |
| `kintone-get-apps`（ID 指定） | **0件** |
| `kintone-get-records` | **`403` 権限なし** |

**守られました。** スペースの中に作ったアプリは、既定でそのスペースの
メンバーに絞られます。

> [!IMPORTANT]
> **ただし、守っているのはスペースの公開設定ではなく、アプリのアクセス権です。**
>
> アプリ側の権限を「Everyone」に広げれば、
> **スペースが非公開でも読めます**。スペースに入れたことは関係ありません。
>
> 確認すべきは**アプリのアクセス権**です。スペースの公開設定ではありません。

人間はアプリ一覧を端から眺めませんが、**Claude は一覧を取って整理して並べます。**
アクセス権が緩いアプリがあれば、その場で表面化します。

→ こちら側で絞るなら `ALLOWED_APP_IDS` です。`kintone-get-apps` の結果もこれで絞られます。
**ただしアプリを絞ると、スペース操作と検索は1つも公開されなくなります**（上記参照）。

### 公開スペースは、メンバーでなくても読めます

`kintone-get-space` が使う API は、
[**非公開スペースの場合だけ**メンバーに限られます](https://cybozu.dev/ja/kintone/docs/rest-api/spaces/get-space/)。
公開スペースは誰でも読めます。

**「スペース一覧」というツールはありません**が、Claude は
アプリ一覧から `spaceId` を拾い、**1つずつ `kintone-get-space` を呼んで**一覧を作ります。
実測で13回／20秒でした。連携ユーザーを設定していれば、
**その13回は連携ユーザーの権限で走ります。**

## 対応しているクライアント

いま確認できているのは **Claude（デスクトップ・スマホ・claude.ai）** だけです。

プロトコルとしては標準的な OAuth 2.1 を話します
（PKCE S256、RFC 9728 保護リソースメタデータ、RFC 8414 認可サーバーメタデータ、RFC 8707 リソースインジケータ）。

クライアントの受け入れ方は2つあります。

### 1. 静的に登録する（既定）

`claude-hosted` を1つだけ登録してあります。
Claude は「独自の OAuth クライアントを使う」を選べるので、これで足ります。

**動的クライアント登録（DCR / RFC 7591）は無効**です。誰でも登録できる口は開けません。

### 2. CIMD で受け入れる（`CIMD_ALLOWED_HOSTS`）

**OAuth Client ID Metadata Document**（draft-02）に対応しています。
`client_id` が **HTTPS の URL** になり、サーバーがその URL を取りに行って、
返ってきた文書をクライアントの定義として使います。**事前登録が要りません。**

ChatGPT が推奨しているのはこの方式です（DCR は「設定すれば使える」扱い）。

```sh
CIMD_ALLOWED_HOSTS=chatgpt.com
```

> [!IMPORTANT]
> **ホストを挙げないかぎり、CIMD ごと無効です。**
> 「誰でも繋げる」を既定にしていません。挙げたホストが配る文書だけを受け入れます。
>
> ホスト名は**完全一致**です。`chatgpt.com` を許可しても
> `a.chatgpt.com` や `evil-chatgpt.com` は通りません。

> [!WARNING]
> **CIMD で来たクライアントの名前は、相手の自称です。**
>
> `client_id` の URL を用意できる者は、名前を自由に決められます。
> 「Claude」と名乗るのは誰にでもできます。
>
> そのため同意画面では、**照合済みのホスト**を主に出し、
> 名前は「こう名乗っています」と添えるだけにしています。

**SSRF について**: URL の取得は `oidc-provider` が行い、
**HTTPS のみ / リダイレクトを追わない / 接続後のソケットの実アドレスで
private IP を遮断（DNS リバインディング対策）/ 2.5秒で打ち切り**
という制約がかかります。こちらはその上に**ホストの許可リスト**を足しています。

## 開発

```sh
pnpm install
pnpm test          # Firestore を使う試験は飛ばされる
pnpm typecheck
```

Firestore の保存層まで含めて試すには、エミュレータを動かします
（手順は [docs/firestore.md](docs/firestore.md)）。

```sh
pnpm emulator      # 別のシェルで
pnpm test:firestore
```

> [!NOTE]
> **飛ばした試験は、テスト名に出ます。**「通った」と読み違えないでください。
