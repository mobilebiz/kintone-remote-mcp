# スペース操作の検証手順

連携ユーザー（パスワード認証）で動く5つのツールを、実環境で確かめる手順です。
[docs/deployment.md](deployment.md#連携ユーザーを有効にするスペース操作と検索) の
設定を済ませてから行います。

> [!WARNING]
> **本番のスペースで試さないでください。** `kintone-delete-space` は
> **スペースに置かれたアプリとレコードごと**消します。取り消せません。

> [!WARNING]
> **スペースは、名前ではなく ID で指定してください。**
>
> 一覧のツールは無く、Claude は
> `kintone-get-apps`（**あなたの権限**）から `spaceId` を拾って一覧を作ります。
> **アプリの無いスペースは、そこに出てきません。**
> 新しく作ったスペースが「検索で引っかからない」のはこれが理由です
> （実際に踏みました）。
>
> ID は kintone の URL に出ています: `.../k/#/space/25` → `25`

## 何を確かめるのか

「動くこと」だけではありません。**境界が主張どおりに効いていること**を見ます。

| # | 確かめること | 壊れていたら何が起きるか |
| --- | --- | --- |
| 1 | 連携ユーザーとして実行される | 本人の権限で動いていたら、そもそも実行できない |
| 2 | **本人に見えないものが見える** | README の警告が推測のままになる |
| 3 | 同意していない接続には出ない | 設定変更だけで既存接続の権限が広がる |
| 4 | アプリを絞ると1つも出ない | アプリ境界の外へ手が届く |
| 5 | 削除は `ALLOW_DESTRUCTIVE` が要る | 「書き込みを許した」が「消してよい」になる |
| 6 | 監査ログで主体と対象が分かる | 共有ユーザーの操作を、誰の何と結び付けられない |

## kintone 側に用意するもの

| 名前 | 種別 | 連携ユーザー | あなた | 用途 |
| --- | --- | --- | --- | --- |
| **スペースA** | 公開 | **スペース管理者** | メンバー | 更新・削除 |
| **スペースB** | **非公開** | **メンバー** | **参加しない** | 到達範囲の確認 |
| **スペーステンプレート** | — | — | — | テンプレートからの作成 |

- スペースAには**捨ててよいアプリを1つ**置き、レコードを1件入れます
- スペースBにも**捨ててよいアプリを1つ**置き、レコードの文字列に
  **`ZZTESTONLY-B`** のような一意な文字列を入れます（検索の確認に使います）
- `kintone-update-space` と `kintone-delete-space` は
  **対象スペースの管理者権限**が要ります
- `kintone-add-space-from-template` は
  **テンプレートからスペースを作る権限**が要ります（通常はシステム管理者）

> [!CAUTION]
> **連携ユーザーにシステム管理者権限を与えると、検証の意味が薄れます。**
> 「権限を絞った専用ユーザー」という前提が崩れ、
> 何が効いて何が効いていないのか分からなくなります。
> テンプレートからの作成（シナリオ5）だけは権限が要るので、
> **そのときだけ与えて、終わったら外す**ことを勧めます。

## シナリオ

> [!IMPORTANT]
> **各シナリオは、新しいチャットで始めてください。**
> そして**最初に「使えるツールを一覧して」と言わせて**、
> 期待どおりの一覧になっていることを確かめてから本題に入ってください。
>
> クライアントはツール一覧を持ち続けます。設定を変えても
> すぐには反映されません（強制は効いていますが、表示が遅れます）。
> 古い一覧のまま総当たりした結果を「機能が動かない」と
> 読み違えます（実際に読み違えました）。

各シナリオの最後に、必ず監査ログを見ます。

```sh
gcloud logging read 'jsonPayload.type="tool.call"' --project=$PROJECT_ID \
  --limit=20 --freshness=30m \
  --format='value(timestamp,jsonPayload.identity,jsonPayload.toolName,jsonPayload.ok,jsonPayload.targets)'
```

### シナリオ1: 参照（済）

**頼むこと**「スペース **<ID>** の情報を見せて」

| 見る場所 | 期待 |
| --- | --- |
| 同意画面 | **連携ユーザーの名前**と「あなたではなく」の断り |
| 結果 | スペース名・アプリ一覧が返る |
| 監査ログ | `identity=integration` / `targets=["space:A"]` |

> **2026-09-18 に確認済み。** 非公開スペースで連携ユーザーが
> メンバーでないものは `403` になりました。

### シナリオ2: 到達範囲（**いちばん重要**）

> [!NOTE]
> **2026-09-18 に確認しました。** 非公開スペース（第三者がスペース管理者、
> 連携ユーザーがメンバー、**接続した本人は非メンバー**）の内容が、
> 本人に返りました。監査ログは `identity=integration`。
> **README の警告は推測ではなく実測です。**

**これを飛ばすと、README の警告が推測のままになります。**

**準備** スペースB（非公開）に**連携ユーザーだけ**を参加させ、
**あなたは参加しない**。

> [!IMPORTANT]
> **スペース ID を直接指定してください。名前で頼んではいけません。**
>
> **「スペース一覧」というツールはありません。** Claude は
> `kintone-get-apps`（**`identity=user`** — あなたの権限）が返す `spaceId` を拾って
> 一覧を組み立てます。つまり実態は
> 「**あなたに見えるアプリが入っているスペースの一覧**」です。
>
> スペースBは「あなたに見えないこと」が前提なので、
> **一覧経由では原理的に到達できません**。名前で頼むと
> 「見つかりません」と返り、**安全だったと誤読します**。
>
> ID は kintone の URL に出ています: `.../k/#/space/25` → `25`

**頼むこと**「スペース **25**（スペースBの ID）の情報を見せて」

| 見る場所 | 期待 |
| --- | --- |
| 結果 | **返ってくる**（あなたは kintone の画面では見えないのに） |
| 監査ログ | `identity=integration` |

**同時に確かめること**: 返った `attachedApps` に、
スペースBのアプリの**名前と説明**が入っています。
これが「本人が見られないものにも手が届く」の実物です。

> [!NOTE]
> ここで**何も返らなかった場合**、次のどちらかです。
> **どちらも「安全だった」ではありません。**
>
> 1. **ID ではなく名前で頼んだ** → 一覧経由になり、あなたの視界しか探していません
> 2. **連携ユーザーがスペースBのメンバーになっていない** → 設定を見直してください
>
> 監査ログに `kintone-get-space` / `targets=["space:25"]` が
> 出ているかで区別できます。出ていなければ 1 です。

### シナリオ3: 検索

**頼むこと**「`ZZTESTONLY-B` を検索して」

> [!IMPORTANT]
> **レコードの中の文字列で頼んでください。スペース名で頼まないこと。**
> 実測では、「検索して」と頼んでも Claude は `kintone-search` を使わず、
> `kintone-get-apps` + `kintone-get-space` で一覧を組み立てました。
> **監査ログに `kintone-search` が出ているか**を必ず確かめてください。
> 出ていなければ、検索は試せていません。

| 見る場所 | 期待 |
| --- | --- |
| 結果 | スペースBのレコードが**ヒットする** |
| 監査ログ | `identity=integration` / `toolName=kintone-search` |

検索は**あなたの視界ではなく連携ユーザーの視界**を返します。
シナリオ2と同じ性質が、より広い範囲で出ます。

> [!CAUTION]
> **2026-09-18 に確認しました。検証の中でいちばん強い結果です。**
>
> 同じ利用者が、同じ会話から、同じアプリ（非公開スペース内、本人は非メンバー）に
> 対して、次のようになりました。
>
> | 経路 | 主体 | 結果 |
> | --- | --- | --- |
> | `kintone-get-records` | **本人** | **`403` 拒否** |
> | `kintone-search` | **連携ユーザー** | **中身が返る** |
>
> **kintone のアプリ権限は正しく効いていました。その上を横断検索が通り抜けます。**
>
> しかも検索結果には `snippets`（検索語の周辺テキスト）が含まれるので、
> **レコードを取得するまでもなく中身が返ります**。
> アプリ ID・アプリ名・スペース名・レコードのURL・作成者も返ります。

> [!NOTE]
> **レコードを作った直後は、検索に出ません。** 索引への反映待ちです。
> 実測では作成の直後が0件、約2時間後にヒットしました。
> **0件を「届いていない」と読まないでください。**
> 先に別の語（既存データに含まれるもの）で検索し、
> **検索そのものが動いていること**を確かめてから判断します。

> [!WARNING]
> **`kintone-search` は横断検索です。** 引数にアプリ ID を持たず、
> 結果を絞る手立てもありません。連携ユーザーが読めるものは全部対象です。

> [!CAUTION]
> **先に kintone 側で「API ラボ」の検索 API を有効にしてください。**
>
> kintone システム管理 → その他 → アップデートオプション →
> 「検討中の新機能」→ **API ラボ** →
> **「kintone全体を検索するREST API」を有効にする**
>
> ⚠ **cybozu.com 共通管理の同名画面ではありません。** 両方にあります。
> 入口は **kintone 側の歯車**です（取り違えました）。
>
> 有効にしていないと `400 GAIA_OF02` で必ず失敗します（2026-09-18 に実測）。
>
> **サイボウズは API ラボについて「テスト環境だけでの利用を推奨します」と
> 明記しています。** 本番で有効にするかは、それを踏まえた判断になります。

> [!NOTE]
> **検索が使えないと、モデルは総当たりに行きます。**
> 実測では、検索が失敗する前に `kintone-get-form-fields` と
> `kintone-get-records` で**約60秒に18回**、アプリを1つずつ舐めていました
> （同じアプリを2回ずつ試すことも）。
> `MAX_CONCURRENT_TOTAL` と kintone 側の API 制限の両方に効きます。

### シナリオ4: 更新

**準備** 連携ユーザーをスペースAの**スペース管理者**にする。

**頼むこと**「スペース **<ID>** の名前を『検証用スペース』に変えて」

| 見る場所 | 期待 |
| --- | --- |
| kintone | 名前が変わっている |
| 監査ログ | `identity=integration` / `targets=["space:A"]` |

> [!NOTE]
> **2026-09-18 に確認しました。** `kintone-update-space` が
> 連携ユーザーとして実行され、監査ログに対象スペースが残りました。
> **連携ユーザーによる初めての書き込みです。**

**権限が無いときも確かめます。** 連携ユーザーが管理者でないスペースを
指定すると `403` になり、監査ログに `failureKind=forbidden` が出ます。

> [!NOTE]
> **公開範囲（`isPrivate`）の変更は、このサーバーが拒否します。**
>
> `kintone-update-space` は API としては公開／非公開を切り替えられます。
> 削除ではないので `ALLOW_DESTRUCTIVE` では止まらず、
> `ENABLE_SPACE_WRITE=true` に含まれてしまいます。
>
> データは消えませんが、**見えなかったものが全社に見えるようになります**。
> 消えるより気づきにくいので、引数そのものを拒否しています。
>
> 確かめるなら「スペース <ID> を公開に変えて」と頼んでください。
> 監査ログに `failureKind=forbidden_argument` が出て、
> **kintone のステータスが付きません**（呼んでいないため）。

### シナリオ5: テンプレートからの作成

**準備** 連携ユーザーに、テンプレートからスペースを作る権限を与える。

**頼むこと**「テンプレート○○から『使い捨て検証』というスペースを作って」

| 見る場所 | 期待 |
| --- | --- |
| 結果 | 新しいスペース ID が返る |
| kintone | スペースができている |

> [!NOTE]
> **`members` に `isAdmin: true` が1件以上必要です**（API の制約）。
> Claude が省くと API 側で弾かれます。
> **作成は即座に本番へ反映され、このツールからは取り消せません。**

終わったら**権限を戻してください**。

### シナリオ6: 削除の歯止め

**まず、有効にしないまま頼みます。**

**頼むこと**「スペース『使い捨て検証』を削除して」

| 期待 |
| --- |
| **ツールが一覧に無い**ので実行されない |

これが `ALLOW_DESTRUCTIVE` の確認です。kintone の書き込みスコープは
削除も許すので、**このフラグだけが歯止め**です。

**次に有効にして、シナリオ5で作ったスペースで試します。**

```sh
gcloud run services update $SERVICE --region=$REGION --project=$PROJECT_ID \
  --update-env-vars="ALLOW_DESTRUCTIVE=true"
```

> [!WARNING]
> **スペースに置かれたアプリとレコードごと消えます。**
> シナリオ5で作った使い捨てスペース以外では試さないでください。

終わったら**必ず戻します**。

```sh
gcloud run services update $SERVICE --region=$REGION --project=$PROJECT_ID \
  --remove-env-vars="ALLOW_DESTRUCTIVE"
```

### シナリオ7: 同意していない接続には出ない

**準備** シナリオ1〜6を終えた接続を残したまま、
`KINTONE_INTEGRATION_USERNAME` を**別の名前に変える**。

**頼むこと**「スペース○○の情報を見せて」

| 期待 |
| --- |
| **ツールが一覧に無い** |

同意したのは「**あの連携ユーザーとして実行されること**」であって、
「連携ユーザー一般」ではありません。名前が変われば同意は無効です。

> [!NOTE]
> **2026-09-18 に確認しました。** 公開されるツールが **17件 → 13件**になり、
> 消えたのは次の4件でした
> （`kintone-delete-space` は `ALLOW_DESTRUCTIVE` が無効なので元から非公開）。
>
> ```
> kintone-get-space / kintone-update-space
> kintone-add-space-from-template / kintone-search
> ```
>
> 監査ログにも、この間の連携ユーザーの実行は1件もありません。

> [!IMPORTANT]
> **クライアントは古いツール一覧を持ち続けます。**
>
> 実測では、Claude 側は 17件の一覧を保持したまま
> `kintone-get-space` を呼び、**サーバーに「ツールが見つからない」で弾かれました**。
>
> つまり**公開の判断は、一覧を作るときだけでなく実行のときにも効いています**。
> 古い一覧を持っているクライアントからも呼べません。
>
> ⚠ 逆に言うと、**利用者からは「サーバーの不調」に見えます。**
> 実際、モデルは「MCPサーバー内部の状態の問題」「再起動したほうが早い」と
> 説明しました。設定を変えるときは、利用者にそう伝わることを見込んでください。

終わったら元の名前に戻します。

### シナリオ8: アプリを絞ると1つも出ない

**準備**

```sh
gcloud run services update $SERVICE --region=$REGION --project=$PROJECT_ID \
  --update-env-vars="ALLOWED_APP_IDS=<スペースAのアプリID>"
```

**頼むこと**（3つとも試します）

| 頼むこと | 期待 |
| --- | --- |
| 「スペース **<ID>** の情報を見せて」 | **ツールが一覧に無い** |
| 「アプリの一覧を見せて」 | **許可したアプリだけ**が返る |
| 「アプリ **<許可外のID>** のレコードを見せて」 | **拒否される** |

スペース系は引数にアプリ ID を持たないので、アプリ境界の判定が**素通りします**。
拒否しているように見えて何も見ていない状態を避けるため、**公開しません**。

> [!IMPORTANT]
> **3つめを飛ばさないでください。**
> 一覧を絞るのと、**問い合わせる前に拒否する**のは別の仕組みです。
> 前者しか効いていないと、**ID を直接指定すれば通ります**。

> [!NOTE]
> **2026-09-18 に3つとも確認しました。**
>
> - 連携ユーザー名は**正しい状態に戻したうえで**試したので、
>   4件が消えたのはアプリ境界によるものと切り分けられた（シナリオ7とは別の仕組み）
> - `kintone-get-apps` は `ids` 指定なしの**全件要求**だったが、返ったのは許可した1件だけ
> - 許可外アプリへの直接指定は、監査ログにこう出た:
>
> ```
> kintone-get-records  ok=False  ['49']  failureKind=app_not_allowed
> ```
>
> ⚠ **`tool.call` は出ます。** 出ないことを期待しないでください。
> 見るのは `failureKind=app_not_allowed` と、**kintone のステータスが無いこと**です。
> ステータスが無いのは、**kintone を一度も呼んでいない**からです。

終わったら戻します。

```sh
gcloud run services update $SERVICE --region=$REGION --project=$PROJECT_ID \
  --remove-env-vars="ALLOWED_APP_IDS"
```

- 使い捨てスペースを片付ける
- **`ALLOW_DESTRUCTIVE` を外したことを確認する**
- [docs/deployment.md](deployment.md#公開前に残っていること) の
  チェックリストを更新する
